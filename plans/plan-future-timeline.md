# AI 规划助手 / Future Timeline Plan

把系统从「被动记录 + 到点提醒」升级为「AI 主动规划 + 用户查询决策」。核心目标：AI 能帮用户安排所有 event 和前期准备，在用户迷茫时能回答「现在做什么 / 最近要做什么 / 要多久 / 在哪做」。

状态：**讨论中，未落地**。本文档只记录问题、候选方案、未决点，不给实施顺序。

---

## 终极愿景（用户原话整理）

> AI 帮我安排所有 event 和前面的准备。在我不知道做什么的时候，问她可以知道要做什么、最近会需要做什么、需要多长时间、有一个事情要做那放在哪做比较好。

拆成四类能力：

| 用户诉求 | AI 需要具备 |
|---|---|
| 「现在能做什么」 | 知道此刻空闲、精力状态、手边能做的事 |
| 「最近会需要做什么」 | 未来 N 天承诺/ddl 的全局视图，能排优先级 |
| 「需要多长时间」 | 每件事的时长估计（用户给 or 历史数据推 or 结构化问答） |
| 「在哪做比较好」 | 每件事的场景约束（家/图书馆/外出），以及用户当前位置 |

这决定了系统定位的转变：**AI 从记录员变成规划者**。

---

## 已确认的设计原则

### 1. 规划的主动权：AI 做 0-1，用户改 1-10

- AI **直接排**准备期/任务到 timeline，不是「建议之后等用户确认」
- 用户看到后可以改——改时间、改时长、取消、换位置
- 理由：减少决策负担是核心价值，「等用户批准」等于把决策还给用户

### 2. 耗时估计：结构化问答（待设计的新机制）

- 暂时不靠纯自由对话硬估，也不强行让用户一次性说清楚
- **用户原话**：「AI 发问卷我来填，最后汇总之后放回原聊天」
- 这是一个**当前系统没有的能力**——需要新机制：
  - AI 生成结构化问题清单（比如 3-5 个问题）
  - 用户填答（Discord 里的表单？多轮追问？网页表单？）
  - 汇总结果写回对话上下文 + 落库成 deadline/appointment 的属性
- 历史 events 同类型项目的实际时长可以作为辅助输入，但不替代用户确认

### 3. 查询触发：双向的

- 用户**主动问**（「我现在不知道做什么」「这周有什么要做的」）
- AI 在**轮询时也会问**（利用现有 PROACTIVE_PROMPT 的「关心/提一嘴」路径，融合「你要不要开始 X」的建议）

## 核心能力拆解

### 能力 1：未来时间规划（0-1）

**输入**：一个 deadline 或 appointment（带耗时估计 + 场景约束）
**输出**：一段或多段「planned event」，排进未来的 timeline

例子：
- deadline「周五交数据科学作业，预计 6 小时，在家做」→ AI 排出「周三 20:00-23:00 写作业」「周四 20:00-23:00 写作业」两段
- appointment「周二 10:00 上数据科学课，课前需 30min 预习」→ AI 排出「周二 09:15-09:45 预习」

**开放问题**：
- AI 怎么判断「空闲时间」？现在没有 availability/日程概念——需要从已有 planned events + appointments 反推，还是让用户先维护「每天可用时间段」？
- 排不下怎么办（时间不够/冲突）？AI 主动 flag 回来让用户决定？

### 能力 2：当前可做推荐

**场景**：用户发「我现在不知道做什么」或 AI 轮询时主动提

**AI 需要什么信息**：
- 现在时间 + 预计空闲时长（用户说「还有 1 小时」还是 AI 推？）
- 用户当前位置/场景（家？图书馆？外面？）——**系统当前完全没有这个维度**
- 当前精力状态（现有 PROTOCOLS 有深度专注/高耗宕机等信号，可能能用）
- 最近要做的清单（deadline + appointment + planned events）

**开放问题**：
- 「位置/场景」怎么获取？用户每次手动说 / 让用户维护几个预设场景 / 从最近的 event 推？
- 推荐输出形式：一个具体建议 / 几个选项 / 给 checklist 让用户挑？

### 能力 3：「最近要做什么」全局视图

**场景**：用户问「这周有啥」或 AI 晨间/轮询时摘要

**和现有 Block 4 的区别**：
- 现在 Block 4 只注入 active 清单的**原始列表**
- 这里需要 AI 能**排优先级、关联相关项**（比如「周五 ddl 作业 + 周四就该开始写」=「本周重点」）

这其实主要是 **prompt 工程 + 展示设计**，数据层改动小。

### 能力 4：耗时估计的结构化问答

见「设计原则 2」。需要单独拉出来讨论：这是一个跨 Discord/Web/DB 的新交互模式。

## 数据模型的影响

原来 plan 问的是「准备期放哪」。现在目标变成「AI 主动规划」，问题重新表述：

**规划的产物是什么？怎么存？**

候选：

**方案 P1：复用 appointment 表，标记 `planned_for` 指向 ddl**
- AI 排的「周三晚上写作业」是一个 appointment，`planned_for_deadline_id` 指向那个 ddl
- 优点：不加表
- 缺点：appointment 语义变了（原本「到场/发生」变成「计划中的工作块」）

**方案 P2：新表 `planned_blocks`**
- 字段：start_time, end_time, content, linked_deadline_id, linked_appointment_id（准备期）, status（pending/done/skipped）
- 和 events 的区别：events 是「已发生」，planned_blocks 是「AI 安排的未来工作块」
- 到点后：如果用户真做了 → 成为 event；没做 → skipped
- 优点：语义干净，独立生命周期
- 缺点：多一张表，timeline 聚合要合并两个来源

**方案 P3：扩 events 表加 `is_planned`**
- events 既存过去也存未来，`is_planned=true` 表示 AI 排的
- 到点后：用户确认 → is_planned 置 false（变真 event）/ 没做 → 删掉或改状态
- 优点：timeline 天然融合
- 缺点：events 语义变、merge 模块要重写、project_name 等字段对 planned 的含义不同

**当前倾向**：P2。理由：
- AI 规划是个**新能力**，值得独立一张表来承载它的生命周期（pending → done/skipped）
- events 表作为「已发生的轨迹」语义不该动
- appointment 的「到场」语义也不该扩

但 P2 的实际数据一致性有复杂性——同一个 deadline 被 AI 排了 3 个 blocks，用户改了其中一个，另外两个要不要重算？需要继续讨论。

## Timeline Future 视图（能力 1 的可视化）

用户原话：「timeline 引入 future，把定好的事直接安排进去」。

在「AI 主动规划」定位下，future timeline 不是手动填的区域，而是**能力 1 的产物可视化**：
- 未来的 appointment（「周六音乐剧」）
- AI 排的 planned blocks（「周三晚写作业」）
- 进行中 / 已完成的 events（现状）

呈现候选：
- **同一条 timeline 横跨过去/现在/未来**，"现在"是一条垂直分隔线
- 未来块视觉上弱化（半透明/虚线边框），表示「计划中」
- 用户在 UI 上可拖拽/点击修改（能力 1 的「用户改 1-10」入口）

**和数据模型的耦合**：
- 选 P2（planned_blocks）→ API 聚合 events + planned_blocks + appointments 三源
- 选 P3（扩 events）→ 一张表查完

- [ ] 结构化问答的交互载体（Discord 表单 / 多轮追问 / 网页表单）？
- [ ] 历史数据怎么用（自动推 → 给用户看让她确认 / 只在 AI 问问题时作参考）？

### 查询侧
- [ ] 用户场景/位置维度要不要引入？怎么维护（手动说 / 预设切换 / 推断）？
- [ ] 「当前空闲时长」用户每次说，还是系统推？

### Timeline 侧
- [ ] 过去/现在/未来同屏还是分区？
- [ ] 用户修改 planned block 的 UI 入口设计？

### 数据清理侧
- [ ] planned block 到点没做（过期）怎么处理？自动 skipped / 询问用户 / 转 event？
- [ ] memory 过期机制——之前 plan 提过，现在在「AI 规划」定位下可能更不紧急（因为准备期不走 memory 了）

---

## 不做的事（明确排除）

- 不合并 deadline 和 appointment——两者的「完成 vs 到场」区分仍然清晰
- 不动 reminder 作为「触发器」的定位——它是执行层工具，不是规划层对象
- 不做「AI 规划后等用户确认才落库」——已确认 AI 直接排（0-1），用户后改（1-10）
- 不做「AI 自主到点执行」（比如自动开始 planned block）——AI 只规划，执行由用户
