# docs 说明

核心原则：**每条信息只有一个家**，其他地方只放链接，不复制内容。

拿不准一份文件放哪，先问它的**时态**：

| 时态 | 回答的问题 | 放哪 | 可变性 |
|------|-----------|------|--------|
| 现在 | 系统当前是什么样 | `codebase/` | 覆盖更新（活文档）可使用skill learn-codebase 生成 |
| 将来 | 接下来打算怎么改 | `plan/` | 改完即归档 |
| 过去 | 当时为什么这么决定 | `adr/` | 不可变 |
| 记录 | 某件验证何时成功 | `OPERATIONS-LOG.md` | 只追加 |

## 目录结构

```
docs/
├── README.md
├── codebase/                 # 【现在】全局现状（跨模块）
├── modules/                  # 重点模块，按模块聚合
│   └── memory/
│       ├── README.md         # 这块现在是什么样（现状入口）
│       ├── design.md         # 当前设计（会演化，覆盖更新）
│       ├── plan/             # 每次迭代的施工方案（改完归档）
│       ├── decisions.md      # 难以反悔的关键决定（极少）
│       └── archive/          # 被推翻的方案、旧版本
├── plan/                     # 【将来】零散的、跨模块的一次性方案
├── adr/                      # 【过去】全局关键决定
└── OPERATIONS-LOG.md  # 运维验证台账（只追加）
```

可执行的东西不放 docs：常规测试进项目根 `tests/`，模型/策略选型评测进项目根 `evals/`。docs 只放给人读的描述性文档。

## 按模块聚合 vs 按类型聚合

- **会长期密集迭代的大模块**（如 memory）：给它一个 `modules/<name>/` 目录，把这块的现状、设计、plan、决定、废弃方案全部收在一起，不打散到全局目录。
- **零散的一次性活**（如接一个日历、一次小重构）：进全局 `plan/` 和 `adr/`。

## design 与 plan 的区别（最容易混）

- `design.md` = 竣工图，描述"现在被设计成什么样"，时态是现在，持续覆盖更新。
- `plan/` = 施工图，描述"这一次打算改什么"，时态是将来，改完归档。

信息单向流动：**plan（施工）→ 采纳的内容毕业进 design（竣工）；被推翻的整篇 plan 移进 archive。**

## ADR 写作纪律

同时满足三条才写 ADR，否则它属于 design 或 plan：

1. 难以反悔的决定；
2. 有被认真考虑、但最终否决的替代方案；
3. 方案已通过 spike 或实际实现验证。

正常速度是每月两三篇。数量失控通常是把设计笔记误当决定了。

## 单任务执行顺序

想清楚 → 做 → 收尾。

1. 写 plan（一页内，标出不敢定的疑点）。
2. 有疑点先做 spike 验证，用结论修正 plan；没有就跳过。
3. plan 稳定后拆成 Linear issue，逐个实现。development log 是全程随手记的草稿，不占步骤。
4. 收尾三查：产生了难以反悔的决定？→ 写 ADR。改了系统结构？→ 更新 codebase / design。plan 和 issue 归档。

大多数任务收尾时**不产出 ADR**，这是正常的。

## Linear 的位置

Linear 只管**状态**（做没做完、下一件是什么），不管内容。

- issue 描述只放三样：一句话做什么、完成标准、指向 plan 的链接。方案细节一律在 plan 里。
- 单人项目只用 Backlog → In Progress → Done 一层，其余功能忽略。维护 Linear 每周超过十几分钟就是在给工具打工。

## AI 使用边界

思考归我，质疑归 AI，提炼归我，格式化归 AI。从讨论中提炼结论必须我本人用三五句话完成，AI 只把结论套进模板，约束是只格式化、不补充、不扩写。
