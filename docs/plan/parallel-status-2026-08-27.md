## 二、LT-170 在 staging 上的实测数据

在这次核查之前，关于 staging 的记录只写了"已部署"，并没有证据说明这个队列是否被真正使用过。
因为容器健康检查通过只能证明进程还活着，不能证明发送路径确实经过了队列，所以我直接查了
容器内的配置文件和 SQLite 库，得到下面这组数据。

- `life-tracker-staging-app` 已连续运行 17 小时，健康检查正常；容器内 `/app/config.json` 中
  `async_pipeline.outbound_queue_enabled` 确实为 `true`，另外两个开关为 `false`。
- `outbound_deliveries` 表累计 **33 条投递记录**，时间跨度从 2026-08-26 11:48 到
  2026-08-27 04:00，覆盖了全部五种来源：

  | `source_type` | `kind` | 条数 |
  | --- | --- | --- |
  | `chat`（聊天回复） | message | 11 |
  | `chat_tool_feedback`（工具反应） | reaction | 3 |
  | `check_in` | message | 15 |
  | `reminder` | message | 3 |
  | `system_alert` | message | 1 |

- **33 条记录的状态全部是 `sent`，`attempt_count` 一律为 1，`last_error` 全部为空。**
  也就是说，运行期间没有触发过任何一次重试，也没有出现过失败。

这组数据说明这个队列不是空转了 17 小时，而是真实承担了全部五条发送路径，
因此合并 PR #14 的把握是足够的。

**但是这组数据能证明的范围要说清楚，否则将来容易读得过宽。** 33 条投递分布在 17 小时之内，
其中最密集的一段是 check-in 的 15 条，平均下来大约每半小时才有一条。在这样的流量下，
队列里几乎不会出现真正的排队，因此**同频道的队首阻塞、跨频道的并发等待、
以及 lease 过期回收这三条路径在 staging 上一次都没有被走到**，它们目前只有
`tests/test_outbound_pipeline.py` 里的单元测试覆盖。这一点不构成合并的阻碍，
因为低流量本来就是这个项目的真实负载；但它决定了合并并在生产启用之后，
仍然需要观察一段时间，而不能把 staging 这 17 小时当作并发路径也已经验证过。

## 三、三处容易被误读或遗漏的地方

**第一，`tool_worker_enabled` 与 `tool_worker_apply` 这两个开关目前没有任何消费者。**
它们只在 `config.py` 里参与合法性校验，校验的内容是依赖方向必须满足
apply ⇒ worker ⇒ outbound；除此之外，整个代码库没有任何一处读取这两个值。
配置文件读起来像是"工具 worker 已经存在，只是暂时关着"，但实际情况是它背后一行实现代码都没有。
将来接手这部分工作的时候，不要因为看到开关就以为只需要打开它。

**第二，`tool_batches` 那一段基础设施连 issue 都没有建。** 这一点在上面第一节已经提过，
之所以在这里重复强调，是因为设计文档第 4.3.1 节其实已经把表结构、lease fencing 机制和
状态机全部写死了，规格是现成的，缺的只是把它拆成 Linear issue 这一步动作。

**第三，PR #14 与 PR #15 之间存在文档冲突。** 这两个分支都修改了
`docs/plan/README.md` 顶部的"关键更新"列表，以及设计文档第 13 节的同一段落。
先合并的那个不会有问题，后合并的必然需要处理冲突。

## 四、下一步的建议顺序

**第一步，把两个已经写完的 PR 合并掉。** 这不是新增工作，而是收尾。
建议先合并 PR #15（LT-171），因为它改动较小、只涉及场景相关的文件；

可以再观察 staging 几天之后另行判断。

**第二步，做 LT-168 人设重写。** 这一点需要说明理由：
这套并行架构**并不解决语气出戏的问题**，设计文档第 10 节和第 12 节都是这么写的，
因为那两百字左右的语气禁令会原样跟着人设进入聊天模型，
真正描写日和是谁的二十七个字与禁令之间的比例一个字都没有改变。
真正解决出戏的是 LT-168，而设计文档第 11 节的人设初稿已经写好了，
它既不依赖双层结构，也不依赖第 0 步剩下的基础设施，现在就可以做完。
与之相比，第 0 步余下的那半截是一个完整的工程项目，做完之后用户在使用上感觉不到区别。
